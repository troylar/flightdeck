# Evidence packs

> **For:** anyone who has to show what happened in a run: an auditor, a reviewer, a change board.
>
> **You'll get:** what a pack holds, how to check it hasn't changed, and its limits.

**On this page:** [What's in a pack](#whats-in-a-pack) · [Checking a pack](#checking-a-pack) · [A pack is a snapshot](#a-pack-is-a-snapshot-of-the-folder-and-says-when-it-isnt) · [Privacy](#privacy) · [Limits and sizes](#limits-and-sizes) · [The readable report](#the-readable-report) · [Command line](#command-line) · [For AI assistants](#for-ai-assistants)

An evidence pack is a zip of what the team folder holds about one run, or about the runs of a process started between two days: the original files, byte for byte, a page to read, and SHA-256 hashes to check them by. Make one from a run's **Receipt** or its **More** menu, from **Runs › More › Export evidence…**, or with `flightdeck export`. Making one never changes the team folder, and a pack is never written into it.

## What's in a pack

| Path | What it is |
|---|---|
| `evidence.html` | A page to read in any browser. It runs no script and loads nothing: its Content Security Policy is exactly `default-src 'none'; img-src data:; style-src 'unsafe-inline'`. Pictures are inline; every other file is listed with its path, size and SHA-256. Anything that changed while the pack was made, and any check that failed, is shown first, in red. |
| `originals/…` | The files, at their paths in the team folder. A name that would clash with another one on Windows (letters differing only in case, or a file named like a folder of the pack) gets " (2)" (always the file, never the folder), and `manifest.json` gives its real path. Names are made unique first and checked after. |
| `manifest.json` | When collecting started and ended, the time zone, which runs and which revisions were read (`run.json`'s `rev` and SHA-256, the run folder's listing), every file with its path, size, SHA-256, what it is and any flag, the generated files' SHA-256, what was left out and why, what's unresolved, and whether this window had unsaved changes. |
| `SHA256SUMS` | The SHA-256 of every file above and of `manifest.json`, in the format `sha256sum -c` reads. |
| `README.txt` | What's in the pack and how to check it. |

**For each run, the pack keeps** every file directly in the run folder: `run.json`, every `notes-*.jsonl` and `history-*.jsonl`, conflict copies (`run.conflict-*.json`), `replaced-*.json`, OneDrive's copies (`run-LAPTOP.json`, `run (1).json`, any `run*.json`) and any other file, plus everything in `files/`, at any depth (all of it counts as attachments). A save receipt (`candidate-*.json`) that `run.json`'s lineage doesn't list is kept and flagged "a save that may not be in run.json". It also keeps the run's follow-up decisions in `followups/<process>/` (OneDrive's copies too, and any that can't be read, flagged), the decisions in `corrections/<process>/` on this run's corrections and on the groups they're in, legacy decisions in `suggestions/<process>/` on this run's suggested fixes, any file in those two folders that can't be read ("couldn't be read; may relate to this run"), and the version the run ran: `map.md`, `types.json`, `publication.json` and its screenshots.

**A run with to-dos comes with what its work rests on** (Flightdeck 4.0). Its to-do records in `proposals/` are packed: the chain of applications from the run's work head, the request and the authority (decision, grant or compound) behind each and every record each one saw, the facts used as evidence and the facts each of those saw, in turn (each one a single fact of the same run; one that isn't, or facts that see each other in a circle, are named and the pack is partial), the runs and plans a to-do was done on, its loops' scope records and child runs, every request fulfilling one of its spreads, its receipt, and the decisions and publication proof of what it kept for next time. When where something kept for next time stands can't be worked out (its process's runs and versions are too big to read here, one of its other runs' files is gone or can't be read, or a run its folder lists has no `run.json` (or only a link) by the time its own folder is listed, or a run folder or notes file there is a link, a listing there fails, or a `run.json` there won't parse, isn't a run or is one any reader refuses (judged by the readers' whole verdict first; one that names another run is judged as that run and only then left out as a copy), or a notes line there is torn, or a decision in its `corrections/` or `suggestions/` folder is a link, or one of its versions can't be read (its folder listed as a link, one of its `map.md`, `types.json` and `publication.json` missing, or a version that doesn't verify: from a newer Flightdeck, or files that don't match its record), or one of those files grows past the one-file limit or the budget for those reads while it's read (each is read in bounded slices, counting the bytes actually read, and each slice takes its room from that budget before it's read, so reads made at once never go past it together; once read, the bytes are confirmed against a fresh size and by reading the file again, slice by slice within the same budget, and comparing SHA-256, so a file that grew, shrank or changed at the same size while it was read is read again within the export's tries and then named as changed), named by its path, or the reading fails), that's named and the pack is partial: the keep's claim is never confirmed, and `test/check_pack.py` refuses a complete pack with a claim it can't confirm. `test/check_pack.py` also checks the manifest's nested shapes before reading anything else: the scope has exactly the export's keys (`run` and `tz`, or `process`, `from`, `through` and `tz`), a time zone it knows and real days in order; each run started on those days in that time zone (one whose start can't be read leaves the pack partial); each run the work depends on is named once, with exactly the export's fields (`key`, `role`, `head`, `chain`, `receipt`, `confirmed`), the receipt its packed run.json names, and confirmed in a complete pack (one called confirmed is established from the pack's own references and checked in full, its role, run, version, chain, head and receipt, and its whole closure as a complete pack's work is checked, by the same walk: every run its own work requires (the runs its to-dos were done on or fulfill a spread of, its children, and theirs in turn), each packed, named and checked in full whatever the manifest says of it, and the run itself where that work reaches back to it (its own chain and closure, checked there once, though it is never its own dependency), every record by its own reader, each fact and each evidence plan, even in a partial pack and before anything else stops the check, so a root that can't be read confirms none; the runs named are exactly the ones the pack's own references find, never the run itself, each in a role those references give it); and a run's receipt metadata (`id`, `state`, `why`) is there exactly when the run has ended, names the run.json's receipt, and says confirmed only when the packed receipt says what the run ended with. The runs its work depends on (its loop children, the runs a to-do was done on, the runs whose spread one of its requests fulfills, and theirs in turn) are checked the same way: each one's chain, requests, authority and receipt, and the run itself as Flightdeck reads it, its version included and packed (a version that can't be read names the version's folder, and one that changes while the pack is made is named too: either way the pack is partial). Two different copies of a record it rests on (a synced "(1)" copy, say) leave it ambiguous: both are packed and the pack is partial. A run folder that can't be listed, a folder entry there that is a link where a child run's folder could be, or a run there whose `run.json` is missing or can't be read, is named by its path and kind, and the pack is partial. The manifest gives the run a `living` section (`head`, `chain`, `receipt`, `records`, `deps`: each run its work depends on, `missing`, `complete`). One read of `proposals/` decides what goes in, and each packed record must be the bytes that read gave (the same SHA-256, whole, so a change in spacing or a version number counts): one that is missing, can't be read, changed while the pack was made or arrived meanwhile makes the pack partial, named by its path, and nothing kept for next time is confirmed from it. Over 5,000 records and runs, no pack is made. A to-do record that can't be read but names the run (a malformed request, say) counts too, even before the run has any to-do applied: the pack gets a `living` section and is partial, naming the record's path and kind. A run without to-dos is packed exactly as before. When `proposals/` itself can't be read, whether a run has to-dos can't be told: `proposals/` is named, the run gets a `living` section that isn't complete, and the pack is partial.

**"Published in vN" comes with its proof.** When one of the run's corrections was published in a later version, that version's `map.md`, `types.json` and `publication.json` are in the pack, and the page names them. A version that lists the correction but whose files aren't all there, or don't check out, gives "Can't be confirmed from this pack", with the reason. `test/check_pack.py` holds every such claim the manifest says is confirmed to its own proof, from the pack alone: the three files packed, read as a version by the shipped checker's rules, numbered N, and the correction in it (listed by the version, or included there by its current decision). Decisions count only as the app reads them: a file in `corrections/<process>/` named `.json` (any case; `ignored.txt`, `.json.bak` or a name without an extension is never a decision), a correction decision its reader keeps (format and envelope, who decided and when, its group and status, and for "It's in vN" a folder naming that version), and only the group's current one (the highest revision; two at the same revision are unresolved), which must apply the correction. A withdrawal counts whoever made it, since the pack doesn't hold every correction in the group to tell its authors: stricter than the app, never looser. The claim is also bound to the correction it names and to the version's own text, by the app's landing rules: the correction is read from the packed originals (a correction or a suggested fix before 1.13 in the run's notes, or the run's keep record), its group is worked out from it and must be the claim's, the version must come after the correction's own, and the version's `map.md` must make the change (as `PF.corrections.satisfied` decides it, read as the outline builder reads a draft; a person's recorded result stands in only for the expected text). A claim whose correction isn't packed can't be verified. Only this run's correction is in the pack, so the version is measured from its own version, and whether an earlier version already had it isn't checked: the pack holds only the claimed version.

**Test runs and steps a run didn't need.** A test run is labeled **Test run** on the page, and its version is its stage: the pack keeps the stage's files from `staged/<process>/<stage>/` and checks them by the stage rules, including that the run's version is the number the stage proposes. A step or gate a run didn't need (`only when`) says Not needed and why, with any earlier answer after it.

**What's left out, always with its reason:** save receipts that `run.json`'s lineage lists ("already included in run.json, which lists it in its lineage"), temporary files left by a save, links (never followed), attachments when you choose to leave them out ("left out, not hashed": listed with their size, never read), and, in the browser, a single file over 100 MB. The people directory (`people.json`) is left out; the page shows names and IDs read from it.

**Checks.** For each run, the page and the manifest say whether the run's copy of its checklist is byte for byte the version's `map.md`, whether its frozen step types are the version's `types.json` (compared as data), whether the checklist fingerprint it recorded matches `map.md`, and whether the version itself checks out. A file this copy can't fully understand (a run from a newer Flightdeck, malformed notes lines, a version it can't verify) is packed as it is, and the page says "This page shows only what this copy understands; the original files are complete." Malformed notes lines are listed by file and line number; two notes with the same ID both appear.

## Checking a pack

The hashes make a graph:

1. `manifest.json` lists the SHA-256 of every payload file: everything in `originals/`, `evidence.html` and `README.txt`.
2. `SHA256SUMS` lists the payload **and** `manifest.json`, but not itself.
3. The pack's own SHA-256 is shown when it's made (in the dialog, with Copy, and printed by `flightdeck export`). Keep it somewhere separate from the pack.

Checking these hashes shows whether the files still match. Compare the pack's own digest with one you kept separately. An unsigned pack can't prove by itself that it hasn't changed, or who made it.

```bash
shasum -a 256 the-pack.zip           # compare with the SHA-256 you kept
unzip the-pack.zip -d pack && cd pack
shasum -a 256 -c SHA256SUMS          # macOS; on Linux: sha256sum -c SHA256SUMS
```

On Windows, `Get-FileHash -Algorithm SHA256 <file>` gives a file's hash to compare with its line in `SHA256SUMS`.

## A pack is a snapshot of the folder, and says when it isn't

- Collecting records when it started and ended. After reading a run it lists the run folder again, rereads `run.json`, checks every file's size and lists the decision folders again. Each file is captured once for the whole pack: sized first, then read and hashed, and every use of it (what goes in, run.json's lineage, the checks, the claims, the page and the pack itself) uses those same bytes, so nothing in a pack can disagree with another part of it. After collecting, every run folder and decision folder is listed again, every record in the pack read again and compared by SHA-256, and every other file's size checked. A file that changed is captured again, and every run planned again around it, up to 2 more times. Anything still changing is listed at the top of the page and in `manifest.json` ("The run changed while this pack was made: notes-w3.jsonl grew."), and the pack is **partial**. So is a pack whose `run.json` is missing (it holds what's there), or a date range with a run whose start can't be read (it's included so nothing is hidden).
- The pack holds what's saved in the team folder. If the window making it has a change to the run that isn't in the folder yet, the dialog says "This window has a change that isn't in the team folder yet. The pack holds only what's saved in the folder." and offers **Wait for the save**; the manifest records it.

## Privacy

The people directory and its email fields are left out. Original records and attachments may contain personal information. Anyone you give a pack to can read everything in it. A redacted report, if one is ever made, would be a separate thing that names its redactions; it would never be the evidence pack.

## Limits and sizes

- Packs are stored ZIP files (no compression), with CRC-32 and UTF-8 names and no Zip64, so they follow PKWARE's limits: at most 65,535 files, and no file, offset or the pack itself past 4 GB. Names are relative, at most 512 bytes, with no `..`, leading `/`, `\` or drive letter, and unique ignoring letter case.
- Before reading anything in full, Flightdeck estimates the size from the listing (files, headers, and the page at its largest: pictures as base64, records escaped) and refuses a pack that won't fit. While writing, every byte goes through checked counters.
- In the browser a pack is made in memory: up to 500 MB on a desktop and 150 MB on a phone-width screen or a device with 4 GB of memory or less, and up to 200 runs. Files are read and hashed 1 MB at a time, with a pause between pieces, and **Cancel** stops between them.
- `flightdeck export` has only the ZIP limits. It streams: attachments are hashed 1 MB at a time and read again when the pack is written, checked against the same size, CRC and SHA-256; a file that changed in between stops the pack.
- Records (run.json, notes, decisions, a version's files) are read in full only after their size is checked, never over 100 MB; a pack's size is first estimated from listings and sizes alone. No file is read before its size is checked (people.json too, up to 4 MB). Other runs and versions of the process, read only to work out where corrections stand, share one budget (64 MB, or a quarter of the cap). Past it, nothing is dropped: decisions on the run's own corrections are still packed (a correction's group is known from the correction alone), each correction's standing says "Can't be confirmed from this pack", and the pack is partial, saying why.
- A picture shared by many runs (a version's screenshot) is shown once on the page; later runs point to it.
- Everything the collection holds in memory is counted as it's read, against one budget (the cap in the browser; 1 GB, or 512 MB of records and pictures, on the command line). Decisions that don't belong to the pack are read one at a time and let go once they're sorted, keeping only a fresh copy of what they say (counted) and their hash. Choosing runs by date reads one run.json at a time, counted while it's read; one too big for the budget can't be dated, so it's included and the pack is partial. Past the budget nothing more is read: what's left is listed as left out ("not read: the pack reached the most it may hold in memory here") and the pack is partial.
- Every attempt starts with the same size check: a file added while a pack is checked is sized, and the cap applied, before a retry reads anything.

## The readable report

**Readable report** in the dialog makes `evidence.html` on its own, labeled "A readable report, not the evidence pack". It leaves out the original files, the hashes of attachments that weren't read, and what conflict copies and other copies say.

## Command line

```bash
flightdeck export "<team folder>" --run release/run-2026-10-17 [--out <dir>] [--no-attachments] [--tz Area/City]
flightdeck export "<team folder>" --process release --from 2026-10-01 --through 2026-10-31 [--tz Europe/London] [--out <dir>]
```

- `--from` and `--through` are days, both included, in `--tz` (this computer's time zone unless you say; it's printed and recorded in the manifest): a run is in when the date a clock there showed as it started (`created`) is one of those days. So a midnight that a clock change skips or repeats (America/Santiago, for one) still puts each run on the day the clock showed.
- The pack goes to `~/Flightdeck evidence/` unless `--out` names another folder. The nearest part of that path that exists is resolved (links included) and must be outside the team folder before anything is created; then each missing folder is made one at a time, and each must be a real folder. The pack's name ends in a few random characters, so two packs made in the same second never share one. It's written as `<name>.zip.partial`, created so it never replaces a file, and given its final name when it's done (with " (2)" if the name is taken). Ctrl+C or a failure removes the partial file, and only one this export created.
- Exit codes: `0` a complete pack, `4` a partial pack (made, with what's unresolved listed), `1` no pack.
- It runs the core and storage code from its own installed `flightdeck.html` (the `pf-core` and `pf-storage` blocks), never a team folder's copy. It reads the folder through a read-only adapter that checks the team folder itself and every folder on a path for links, decodes text as a browser does (UTF-8, a byte-order mark dropped; the original bytes are packed as they are), opens files without following links, and then walks the path again: every folder must still be the same real folder, and the file at the path must be the one it opened, so a folder swapped for a link (even one put back afterwards) is refused. A link is left out and named.

## For AI assistants

An assistant may run `flightdeck export` when a person asks for a run's evidence, with `--out` outside the team folder. It never puts a pack, or anything unpacked from one, in the team folder, and gives the person the SHA-256 it prints.
