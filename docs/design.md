# Flightdeck design

Status: **describes Flightdeck 1.17.0** (large-folder slices 1a and 1b, and insights; search and evidence export are planned). Sections marked *planned* describe decided work that isn't built yet. Supersedes the v0.1 "lightweight checklist" scope.

## 1. What Flightdeck is

Flightdeck manages the team's **development processes across their whole life cycle**: PRs, merges, check-ins, sprints, releases, incidents, and how we run our skills. It's a process management tool first.

- Each process has a **checklist**: its written, versioned definition. People run it; **runs** record what actually happened, which keeps the checklist honest.
- **Processes become skills.** A main goal: write the process as a checklist, prove it with runs, then have an AI assistant (outside Flightdeck) build a skill from the validated version. Flightdeck records which skills implement which process versions and steps, and says when a process change means a skill must be updated. Change the checklist first, then the skill. Manual work stays first-class (Manual steps stay fully supported when a tool has no API access).
- **The team owns Flightdeck**, its code and its checklists. Everything is written so any team member, or their AI assistant, can pick it up.

Principles:

- Checklist Manifesto discipline: short steps, gates at natural stopping points, must-dos that can't be skipped, READ-DO and DO-CONFIRM. (Atul Gawande, *The Checklist Manifesto*.)
- One HTML file, offline, opened in Edge or Chrome. Data lives in a shared OneDrive folder.
- No AI inside the app. An AI assistant writes checklists and proposals as files; Flightdeck reads, validates and runs them.
- Calm, clear and beautiful in the middle of real work. Delight comes from clarity, not decoration.
- Not security-sensitive, but no secrets, tokens or customer data in checklists, notes or attachments.

## 3. Concepts

| Term | Meaning |
|---|---|
| **Process** | A thing we do repeatedly (`release`, `check-in`). Has an ID and an owner. |
| **Checklist** | A process's written-down definition: phases, gates and steps, in Markdown. Called a map before 1.10.0; files and code still say `map`. |
| **Publication** | One immutable, numbered version of a checklist plus the step types it uses. Runs always pin a publication. |
| **Run** | One execution of one publication. |
| **Phase** | A group of steps done in order, presented as READ-DO or DO-CONFIRM. |
| **Gate** | A validation point at the end of a phase. Work after it stays locked until it's passed or waived. |
| **Step** | One typed action inside a phase. Every step has a type; there's no generic step. |
| **Step type** | A reusable kind of step with an icon and fields (`confirm`, `ui.action`, `run.command`…). |
| **Recorder** | The one person (one browser window) who records a run in v1. |

## 4. Team folder and writers

Every file has exactly one writer, so OneDrive never has to merge two saves.

```
<team folder>/
  AGENTS.md                        the contract for any AI assistant: Flightdeck's part between markers, then the team's Team notes
  people.json                      shared people list (the folder owner or backup owner, in Settings → People; Flightdeck once, when a team starts)
  maps/drafts/<process>.md         drafts (an AI assistant, or people in the app's editor; saves are checked)
  publications/<process>/v<N>/     immutable once written
      map.md                       the published checklist, with step IDs
      types.json                   copies of every step type the checklist uses
      publication.json             who published, when, change note, content hash
  step-types/<type>.json           team step types (an AI assistant, or people in the app's Step types page)
  images/<process>/...             reference screenshots used by checklists
  runs/<process>/<run-id>/
      run.json                     the run: answers, gates, details, outcome (only the recorder's window writes)
      notes-<session>.jsonl        notes and corrections from one viewer's window (that window writes)
      files/...                    attachments, uniquely named by whoever adds them
  corrections/<process>/<group>.<session>.<rev>.json   one decision on a group of corrections (written once by that window)
  suggestions/<process>/<id>.<session>.json   decisions on suggested fixes from before 1.13 (read, no longer written)
  followups/<process>/<run>.<follow-up>.<session>.<rev>.json   what became of one follow-up (written once by the window that decided)
  proposals/<id>.json              planned runs: an AI assistant writes its own; Flightdeck writes plan-<process>-<random>.json once, for a person
  history/drafts/<process>/<window>.jsonl     saved history of a draft: one line per save in that window (that window appends; an AI assistant may append its own agent-<name>.jsonl)
  history/step-types/<id>/<window>.jsonl     saved history of a step type (that window appends)
  .flightdeck/skills/...           the Flightdeck skills for AI assistants (flightdeck install or flightdeck skills)
  .flightdeck/installed.json       which defaults AGENTS.md's managed part and the skills are based on (flightdeck install or skills; Flightdeck once, when it starts a new folder)
  .flightdeck/updates/<version>/   new defaults the team must merge, with a README.md, and replaced/ copies from --force (flightdeck install or skills; deleted by whoever merges)
  connection/
      probe-<time>-<id>.<window>.json    a connection check (the window that sent it, once)
      ack-<check id>.<window>.json       an answer to one (the window that answered, once)
```

`connection/` is the one documented exception to one writer per file: any window may delete a check or answer older than 7 days (section 21).

`AGENTS.md` has two writers by design, split by its markers: `flightdeck install` owns the part between `<!-- flightdeck:begin -->` and `<!-- flightdeck:end -->`, and the team owns Team notes below it. Install compares each contract file with `src/baselines.json` (every default ever shipped, by hash) and the folder's `installed.json`, so it updates only what is still a default; see docs/updating.md.

A **session** is one browser window. A person on a laptop and on a remote desktop is two sessions, so two writers, so two files.

## 5. Checklists

```markdown
---
process: release
title: Production release
owner: person-casey
context: ticket, commit, environment
roles: release-lead, qa, backend
---

## Before production changes · DO-CONFIRM  {#prep}
- [!] {confirm} Change approved and linked to the release ticket @release-lead {#approved}
- [!] {ci.gate} Full test gate green on the release commit ^commit {#tests}
  > Run the gate after the rebase. A green run on an earlier commit doesn't count.
- [ ] {communicate} Post "starting release" in the team channel @release-lead {#announce}

## Gate: Ready to deploy · owner @release-lead  {#ready}
  approves: deploy of ^commit to ^environment

## Deploy · READ-DO  {#deploy}
- [!] {ui.action} Approve the deploy in Jenkins @backend {#approve}
  system: Jenkins
  deadline: external
  > Jenkins rolls back if nobody approves within 30 minutes. Copy its deadline here.
```

- **IDs** (`{#name}`) are written into the checklist and kept across versions, so notes and skill links follow the same step after edits. The AI assistant adds them. Publishing rejects a missing one rather than inventing it (see section 6). Never reuse a retired ID.
- `@role` assigns; people are assigned to roles per run. `^field` ties a step to a run detail. `>` lines are notes; `![caption](images/…)` are screenshots.
- `approves:` makes a gate say exactly what it authorizes ("Approve deploy of `abc123` to production?").

## 6. Publishing and versioning

- **Anyone can publish.** Publishing validates the draft, freezes the checklist and the step types it uses into `publications/<process>/v<N>/`, and writes `publication.json` (who, when, change note, content hash). That file is the log.
- **Publications are immutable.** A correction is a new version.
- **IDs are written, not invented.** Every phase, step and gate needs an ID. Publishing rejects a missing or duplicate ID (including the automatic `<phase>-confirm` gate IDs) instead of assigning one; the AI assistant adds them when it writes a draft.
- **Runs pin a publication** and render from it forever, even if step types change later.
- **Incomplete or clashing publications are detected, not guessed:** if `map.md` is there but `types.json` hasn't synced yet, the version shows as "still syncing" and can't start a run. If two people publish v5 at once, Flightdeck shows both and asks for one to be renumbered.
- **A version this copy doesn't understand is never run.** A version whose `publication.json` names another format, whose `map.md` has lines the checklist parser doesn't understand (a newer copy's syntax, or a hand or AI edit), that uses a step type that is neither built in nor in its own `types.json`, or whose `types.json` holds a type this copy can't fully read (a newer type version, or a property, field kind or evidence kind it doesn't know; `PF.types.understood`) shows as unusable with the reason, and can't be started, planned onto or picked (`PF.publish.verify`). Only what the version itself holds is checked, never the folder's people, screenshots or Jira workflows, so a version that published cleanly stays usable. A run on such a version (its own checklist copy, or the publication format it names), a `run.json` with fields, states, Jira workflow data or non-text values this copy doesn't know, or a run file in a newer run format (listed by name only, with no steps) opens read-only and is never saved over by this copy (`R.sanitize` and `repo.loadRun` mark it, `repo.saveRun` refuses it). Read-only runs can't be planned again either. **Known limit:** complete versions are cached, so routine refreshes never reread them. A version replaced in place in the folder (same folder name, newer format or content) still shows as usable in lists until the next deep refresh (the Refresh button). Nothing can ever be recorded or saved against it, though: every save and every reread of the open run checks that run's own publication record (one stat while its size and time are unchanged, otherwise a read) and refuses a newer format, or a record whose contents (hashes, folder or version) differ from what this copy verified or the run was started from. Such a version can't be recorded on or started until it's checked again; the next refresh does that, and lists it as unusable if it is.
- **History:** every version of a checklist is listed with its change note, publisher, the runs made with it, and a diff against the previous version.

## 7. Runs (v1)

**States:** planned, running, completed, stopped, cancelled. A running run can be paused with a reason; while paused, steps, gates and timers stand still (1.8.0).

**One recorder.** Only the recorder's window writes `run.json`. Other windows are read-only viewers; while a run is open they reread just that run every 5 seconds. **Hand off** saves the run and names the exact revision passed on; the old window stops writing, and the new recorder's log records which revision they picked up. **Take over** is for emergencies: if the old computer had changes OneDrive hadn't delivered, they arrive as a conflict copy to review. One writer per file is a discipline that prevents ordinary conflicts, not a guarantee across disconnected computers (see `docs/onedrive.md`).

**Everyone can contribute** notes and attachments on any step. Each window writes its own `notes-<session>.jsonl`, and every window shows them all, attributed and in order.

**Attachments (1.13).** A note or a correction can carry up to 10 files: dropped on its box, pasted, or chosen with Attach. Allowed: PNG, JPEG, WebP and GIF images, PDF, text (`.txt`, `.log`, `.md`, `.csv`, `.json`, `.yaml`) and `.zip`, up to 10 MB each (`PF.attach.check`; the extension and the browser's MIME type must agree, and the first bytes must match the kind, `PF.attach.sniff`). Anything else is refused next to the box in plain words. A file is saved in the run's `files/` folder as `<time>-<random>-<window>-<cleaned name>` (letters, digits, dots, dashes and underscores only; never a path, never hidden), and the note records `fileInfo` {path: {name, size}}. Images show as thumbnails that open the viewer; text files open in a dialog as plain text (put in with `textContent`, never markup, first 256 KB); PDF and `.zip` save a copy as plain bytes. Nothing attached is ever shown as a web page or an SVG. **Older copies:** a 1.13 path matches what 1.12 and earlier keep (`runs/…/files/` and `[\w.@/-]`), so an older copy keeps every note and file; it shows images and ignores the rest (test/fixtures/notes-attachments-1.13.jsonl).

**Answers per step:** done, done differently (with what happened; section 19), N/A (not for must-dos), or blocked (with a reason). A blocked step **stops the run** until it's resolved.

**Re-checks:** changing a run detail (commit, environment) sends every step and gate tied to it back for a re-check. Each step keeps its earlier answers (who, when, "did it differently") as history, so a re-check never erases evidence.

**Saving is honest:** each run shows three separate facts: when this computer saved, when it last checked the folder, and whether the folder can be read. Saves happen one at a time, in order. A save that fails stays on screen (refresh doesn't wipe it) with **Try again** and **Discard my change**. Before each save, Flightdeck compares the file's exact contents with what it read; if anything differs, or the file is unreadable, it never overwrites it, and writes this window's version next to the run as a conflict copy.

**Recovery happens in the app:** a run with conflict copies (Flightdeck's or OneDrive's) shows a panel to compare each one with the current version, keep it (recorder only), or delete it. Nothing is merged automatically.

**Run files are checked on load:** unknown answer states, bad IDs and odd values are dropped, so a hand-edited or damaged file can't break the page. Because dropping them would erase what a newer copy wrote, a run file with fields or states this copy doesn't know is shown read-only and never written.

**Retention:** runs are kept forever, grouped by checklist version. Ended runs are archived from the home screen, not deleted. To keep `run.json` small to read and save, it holds the latest 300 log entries and 10 earlier answers per step; **anything older is appended to the run's `history-<window>.jsonl` before the save, never dropped**, and is shown on request ("Show older answers"). Notes are appended, never rewritten. Back up the team folder like any OneDrive folder; restoring it restores every run.

**Finishing a run:** **End run** opens a short finish step: follow-ups (work the run turned up, with an owner and a Jira ticket), the run's corrections (each correction and each step done differently, with where it stands, and Make it a follow-up), then the outcome. The receipt follows, with evidence, follow-ups (each with where it stands) and Corrections · N on it. This is how a run makes the next one better.

**Follow-ups after the run (1.16).** Showing a follow-up on Home for 30 days and then dropping it wasn't resolution; now each one is open until a person says what became of it.

- **Dispositions.** Open → **Done** (an optional link and note), **Moved to a ticket** (a ticket key like `ABC-123`, or its link; required), **Moved to another run** (a running run or a plan from the folder, or a link; one is required, never the run it came from) or **Won't do** (a reason is required: "Why won't it be done? Say why."); **Reopen** makes it open again. Anyone who has said who they are can set them, on any run, ended or not. Links stay `http(s)` (`U.safeUrl`).
- **Storage: no new writer.** The follow-up itself stays in `run.json`, written only by the recorder, exactly as before (`R.addFollowUp`; the run format is unchanged). Each decision is a new file written once by the window that decides: `followups/<process>/<run>.<follow-up>.<window>.<rev>.json` = `{kind: "followup-decision", fv: 1, process, run, followUp, status: open | done | ticket | moved | wont, link?, note?, ticket?, to?: {run: "<process>/<id>"} | {plan: "<id>"}, reason?, by, at, rev, seen}` (`repo.decideFollowUp` refuses if that name exists). Ordering is causal, exactly as for corrections' decisions: `rev` is one more than the decision the person saw, `seen` names its file, the highest `rev` counts, and two at the same `rev` are picked by file name the same way everywhere and show as **Needs review** (still open, with every action) until someone decides again. OneDrive's conflict copies of a decision are decisions too: the canonical `<run>.<follow-up>.<window>.<rev>` name, then any copy marker before `.json` (`-LAPTOP`, ` (1)`, `-LAPTOP José (1)`; a marker never starts with a digit or a dot), so a clash they carry shows as Needs review. `rev` is a whole number from 1 to 1,000,000 and the rev in the file name must match the one inside. A file that can't be read or checked (any field of the wrong type, an unknown status, another name) is listed as unreadable (Folder health), on its own, never a reason to drop the others. A shared folder has no create-if-absent: `repo.decideFollowUp` claims the name in this window first (only this window writes names with its own window part, so a second save of the same name is refused), refuses if the file exists, and announces nothing until the file reads back as exactly what was written. Each follow-up's form has its own element IDs (`PF.followups.formId`, a lossless encoding of its key, never a hash), so what's typed for one is never saved with another. Saving is tracked per follow-up: while one saves, its Save reads Saving… and is disabled, another's form stays open and saves on its own, and a save that finishes closes only its own form. A save that finishes after switching folders never blocks the new folder. Rules in `core/followups.js` (`PF.followups`).
- **Older copies.** Copies before 1.16 never list `followups/` (their loaders read only the folders they know; `test/folder.test.js` proves it with a copy lacking the loader), and `run.json` is untouched, so they show follow-ups as before and keep every run writable. `check_folder.py` doesn't read the folder.
- **Where they show.** Each follow-up has a status pill (Open, Done, Moved to a ticket, Moved to another run, Won't do, Needs review) and, once decided, what became of it with who and when: in the run's Follow-ups utility (with the actions, and Remove for the recorder), on the finish page and the receipt (card and text). **Home** lists **Your follow-ups**: open ones you own, however old (resolved ones drop off), with the actions; never counted in Needs you. **Runs › Follow-ups** (also from Folder health) lists them across runs with Open (oldest first), Yours and All, each with its owner, how long it's been open, a link to its run, and the actions. Each row's actions are a group named for the follow-up; choosing one opens a short form below it (labels above boxes, errors next to their box, Cancel returns focus to the button).
- **Folder health.** "N follow-ups open for more than 30 days" is worth a look (warn), with **Review follow-ups**; none reads "No follow-up has been open for more than 30 days."
- **Assistants** read `followups/` and never write it (`example-folder/AGENTS.md`).

## 8. Gates

- A gate sits at the end of a phase. It **passes** when every step in its phase has an answer, nothing is blocked, and its owner (or the recorder) confirms. It can **fail**, or be **waived** with a reason; must-do steps can't be waived, and a gate can't be waived while any step in its phase is blocked.
- A gate records **what it approved**: the run details it depended on (commit, environment), when and by whom.
- **If anything a passed gate depended on changes** (a detail, a reopened step), the gate goes back to "needs review" and **stays there until someone passes it again**. Re-doing the step doesn't quietly restore the old approval. Reopening never undoes external work; that stays in the record.
- **Gates are not live locks.** Over OneDrive, another screen may be seconds to a minute behind. So a gate means "passed for this commit and environment, by Casey, at 9:52," never "safe right now." **Irreversible actions always keep a person's explicit confirmation**, even when a skill does the work.

## 9. Time

Five different things, never mixed:

| Kind | Example | Source |
|---|---|---|
| Expected duration | "usually 20 min" | the checklist |
| Elapsed | "running 12:40, Blake" | when the step was started in Flightdeck |
| External deadline | "Jenkins rolls back at 21:30" | **copied from Jenkins**; Flightdeck's clock is never the authority |
| Scheduled time | "readiness meeting at 15:00" | the checklist: `at:`, `due:` (clock times on the run's day, in the run's time zone) or `after:` (from the run's start) |
| Due time | "PRs merged by noon" | the run plan (later stage) |

Times are stored as absolute instants with the run's timezone. Moving a release window never moves an external deadline.

## 10. Step types (v1)

A short, broad list. A specialized type earns its place only when it changes behavior (validation, a field, a warning).

| Type | For |
|---|---|
| `confirm` | Checking something is true |
| `communicate` | Telling people something |
| `meeting` | A scheduled conversation |
| `decide` | A go/no-go or choice |
| `review` | Reading or approving a document |
| `wait` | Waiting on someone or something outside the team |
| `ui.action` | Doing something by hand in any other web tool |
| `jenkins.job` | Starting or following a Jenkins job by hand |
| `bitbucket.pr` | Opening, reviewing or merging a pull request |
| `github.pr` | Opening, reviewing, approving or merging a GitHub pull request (1.14.0) |
| `jira.issue` | Creating, updating, moving, assigning or linking a Jira issue by hand |
| `run.command` / `run.script` | Running a command or script (shown as copyable text; Flightdeck never runs anything) |
| `run.skill` | Running a skill |
| `ci.gate` | A build or test pipeline result for a specific commit |
| `jira.sprint` | Starting or closing a Jira sprint, moving its unfinished issues, or setting its goal (1.14.0) |
| `deploy` | Deploying a version to an environment, with what to roll back to (1.14.0) |
| `verify.health` | Watching a dashboard or metric for a while and saying whether it stayed healthy (1.14.0) |
| `measure` | Recording a number with its unit, like velocity or capacity; `sets:` can make it a run detail (1.14.0) |

- **Every type has fields that fit it**, in two kinds: *checklist fields* that describe the step (the Jenkins job and parameters, the repo and branches, the Jira action and target status) and *evidence* that can be noted when it's checked (build number, PR link, merge commit, the decision). The full list is in `docs/map-format.md`.
- **Typed doesn't mean filled in.** A checklist may name only what's known; a step can be there for information, so people and skills know what it involves. Missing usual fields are tips, not errors. Wrong values (an action the type doesn't have) block publishing.
- **Evidence is optional unless the checklist says `require:`** (`require: build` or `require: all`). Releases use it; most processes don't. A plain step always checks in one click.
- **Values can be filled in mid-run.** Some aren't known until the middle of a release. The recorder can fill in or correct a step's values for this run, before or after it's checked. Each change is logged, the checklist's own value stays visible, and filling in never triggers a re-check (except correcting a value the step set with `sets:`: later steps that used it go back for a re-check) (changing a run detail like the commit still does).
- Recorded values appear on the step, in its earlier answers after a re-check, and on the receipt.
- Commands and parameters substitute run details as display text only. Values aren't shell-escaped, so the person reads before running.
- Transitions are checked against `jira/workflows.json` when the folder has it: the status must exist and be reachable, and checking the step asks for the transition's required fields (1.8.0). Without the file, the target status is recorded as written.

## 11. Screens and the delight bar

- **Home: only what needs you.** "Release 2026.10.16: you're recording. Deploy: 3 steps to go." Each to-do has one button. The process list, the skills and both hierarchy trees live in their own sections (Processes, Skills; see section 18), not on Home.
- **Run: a workspace of its own (1.13).** Like the draft editor, a run fills the window, and only its panes scroll:
  - **Header:** Runs, the run's title, process, version and start; `7/14 answered` with a progress bar (said in full to screen readers); Details, Screen share (team runs), Receipt, Finish the run once every gate is settled, a More menu (End run, Plan another like this, Check the folder now, Keyboard shortcuts) and who you are.
  - **Status strip:** who records, with the control that goes with it, and on the right what this window saved and when it checked the folder (separate facts; neither proves another computer has the change). One state at a time: recording here (revision, Pause, Hand off), following (Take over, with its warning), you in another window (Record here), recording waiting for you (Pick up), a handoff still syncing (no pickup yet), paused (reason, who, when; Resume for the recorder, pickup or take over for others; deadlines from tools keep counting), ended (outcome, who, when; Receipt), read-only in this copy (the reason; no recording or take over), and no identity yet (choose who you are). Saving… while a save is in flight; a failed save replaces the reassurance with Try again and Discard my change; conflict copies add Compare copies. The run's details sit beside it; everything else is in Details.
  - **Under the strip:** messages, the failed save's reason, folder trouble, the recovery panel and Details stay in view.
  - **Phases | Checklist | Selected step.** The rail names each phase with its answered count and its gate's state (Passed, Waived, Needs review, Failed, Ready, Waiting on steps, Locked), marks the current phase, and keeps Day timeline, Follow-ups and Keyboard shortcuts. Below 1100 px it becomes a Phases picker with the same utilities at the top of the checklist. The checklist starts with **Next up** pinned at its top: the run's place by the headline rules (a blocked step, a gate to review, failed or ready, the next unanswered step in order for the recorder or your own step for anyone else, with its track and the other tracks' counts, paused, ended, finish), never what this window is looking at. Next up only navigates (Go to step, Back to it, Show blocked step, Review "gate"); it never checks anything. Rows are compact: a check (role checkbox) and a separate select control, the type, who, short target details, state and timing badges; amber marks the run's place, an outline marks the selection. Finished phases fold to a summary (`5 done · 1 N/A`) with the gate's exact approval kept in view; later phases fold with Preview steps; a gate back in review unfolds with its earlier approval. A gate that can't pass says why next to its disabled button (`3 unanswered steps`).
  - **The inspector** changes as a whole with the selection: where it is, Previous / Next, the title, type, who, state and reason; What to do (hint, instructions, values with Copy or Open, reference screenshots with "This screenshot is wrong", the child run, timing with Start and Set deadline); Record the result (evidence boxes, recorded values, Fill in); the answer controls in a group kept in reach while it scrolls (Done primary, Blocked, then N/A, Unblock, Undo N/A or Uncheck; a child-run step has Start instead of Done); Done differently beside Done (or "Did it differently? Say how" after the answer); the step's Corrections · N and Correct this step; earlier and archived answers; notes with attachments, Make it a follow-up, and the note box.
  - **One target for completion:** the row's check and the inspector's Done are the same action on that step. Evidence boxes showing for the selected step are always collected, so Done never ignores what was typed; required evidence not typed yet selects the step and focuses its first box. Checking the step Next up pointed at selects the next open step in its phase and focuses its check (Space continues), announced once ("… checked. Next: …"); the last one leads to the gate's own button, which still asks to confirm. ## 13. Process-to-skill traceability (1.9.0)

Outside the team this is usually called **SOP-to-skill** conversion: turning a standard operating procedure into an agent skill. Flightdeck's part is **process-to-skill traceability**: every skill links to the published process version and steps it follows, runs are the evidence, and a process change that affects a skill is flagged (a change to the skill itself isn't detected).

- **The loop:** publish a version → run it until it's proven → its owner signs it off → an AI assistant builds the skill from Flightdeck's brief → the skill is registered in `skills/<name>.json` → when a later version changes the steps it covers, Flightdeck flags it and writes the update brief.
- **Skills live anywhere** (a repo, a shared folder, a local path). The registration records `location` (the skill's source path or link), the skill's own `version`, `implements: <process>@<version>`, and optionally the `steps` it covers; without `steps` it implements the whole process. A process can have many skills.
- **Status** (`core/skills.js`): current; behind but its steps didn't change (note the version); needs an update (its steps changed, with the exact differences); or can't be matched.
- **Ready for a skill:** at least 3 completed runs on that exact publication that are clean (no block, re-check, N/A or "did it differently" on the covered steps, in any earlier answer either), plus the owner's sign-off in `validations/<process>.v<N>.<writer>.json`. A sign-off counts only for the publication it was made on. **Backup owner (1.15):** a checklist's `backup:` (a person ID) may sign off only while the owner is inactive or not in `people.json`; the record says `"as": "backup"` (kept when sign-offs are read) and `PF.skills.signoffs` counts it. Absence must be read, never assumed: while `people.json` can't be read or lists nobody, or the backup is inactive or not listed, nobody signs as backup, and the sign-off action checks again when clicked. Copies of Flightdeck before 1.15 count only the owner's sign-offs, so they show such a version as not signed off yet. Folder health flags a checklist whose owner or backup is inactive or gone (and says the backup can sign off meanwhile), and the folder owner or backup owner being inactive, missing or doubled.
- **Briefs** are plain Markdown: the steps and run details, what changed, and what people actually did differently (as information, never instructions). Flightdeck copies them; the `flightdeck-skill-brief` skill builds the same from the folder.
- **Hierarchy and tags:** checklists and skills say `group: Engineering / Releases` and `tags:`. The Processes and Skills sections show them as foldable trees with a tag filter.

### Corrections (1.13: slice 1 built; 1.16: slices 2 and 3 built)

A run is the record of how the work really went, including where the checklist was wrong. A **correction** is about one step: what the checklist said, what it should say, and, when the step was done another way, what happened. It belongs to the run it was made in and travels to the process page. Owner decisions: the name is Correction; it's step level; it's part of the run's record; anyone accepts or declines; declining needs a reason.

- **Correct this step** (anyone who has said who they are, in any run state, viewers too): a proposal; it never answers the step, and Done, Blocked and N/A stay. It opens on the wording, filled in with the published text and the caret at the end, with a live Before/After redline (`<del>`/`<ins>`, plus a plain "Before: … After: …" for screen readers). Unchanged wording disables Save with "No wording changed." beside the box. **Change something else** (a menu button) offers Add a missing step (after this step or at the end of its phase), Move this step (after any step, or the start of a phase), Change who does it (the checklist's roles), Replace a screenshot (only when the step has one; also from the screenshot itself), Remove this step from future versions (a reason is required) and Describe another problem. Why is optional otherwise. Files can be attached (drop, paste or Attach), as for notes. C opens it on the selected step; Escape closes its menu, then it. Saving says "Correction saved on this computer." and never claims the team has seen it.
- **Done differently** (the recorder, on an answerable step in an open phase, not while paused, not on a child-run step): an answer. What happened is required, first; then "Should the checklist change?" Just this run (default) or Fix the checklist too, which reveals the same correction fields; the line above the button says the consequence ("Marks this step done differently." / "…and proposes a checklist correction."). Every rule of Done applies first (`R.doneDifferently` calls `done`): required evidence typed in the step's boxes goes with it and errors appear next to those boxes; it's never a way around evidence, a pause, a closed phase or a child run. With a correction, the note is written first, then the run: if the note fails nothing changes; if the run's save fails, the correction stands on its own and the save offers Try again. The answer is made on the run that started it even if the person has moved to another page; if it can't be (the run was paused or its phase closed meanwhile, or its save was refused because the run changed elsewhere), the run shows "Correction saved; the step wasn't marked done." with Mark it now until someone acts. While it's finishing, that step's Fill in is disabled with "Finishing the answer…". Success is said only once the answer is in the team folder (1.13.1); a save waiting for Try again says so. Choosing an open composer's button again only focuses it. Sizes come from one table, `PF.corrections.LIMITS`, used both when a correction is made and when it's read back. A done step without one offers "Did it differently? Say how". Afterwards the step shows "Done differently · who · when" with View correction and Change answer.
- **The published instruction stays visible.** A proposal never replaces the step's text anywhere in the run.
- **Format, no new writer.** A correction is a note in its author's own `notes-<window>.jsonl`: `kind: "correction"`, `cv: 1`, `version`, `folder`, `target {phase, step}`, `step`, `from` (the step's text in that version), `base` (`stepSig`: a hash of the step's type, text, marks, roles, details, fields, note, screenshots and track, without its line), `change` (`{op: wording, to}`, `{op: add, text, where}`, `{op: move, to: {after} | {phase, where}}`, `{op: roles, to}`, `{op: screenshot, shot}`, `{op: remove}` or `{op: describe}`), `why`, `happened` (only with Done differently), `files`, `fileInfo`, and `text`, a plain summary. `run.json` is unchanged: Done differently writes `steps.<id>.differently {note, by, at}` as before, and the answer takes the correction's `at`, so the record joins exactly that answer to that correction; any other answer on the step, earlier or later, is its own row, and a correction whose answer an older copy rewrote still shows what happened on its own. (The plan's `differently.correction` field was left out on purpose: a run with an unknown field opens read-only in 1.11.1 and 1.12.)
- **Older copies.** 1.12 and earlier show an unknown note kind as a plain note with its `text`, and keep its files (`test/fixtures/notes-corrections-1.13.jsonl`). A correction with a newer `cv` or an unknown `op` shows here as Describe another problem, with its own `text` summary as the problem. Step, phase and role names in a change follow the checklist format's limits (60 characters).
- **Groups.** Corrections with the same process, step, `base` and change (exact, apart from leading, trailing and repeated spaces; never case-folded, since wording can hold commands and paths) are one group: "Suggested in N runs" (distinct runs, with names, dates and links inside a disclosure; never a vote). A group's ID is a hash of that content, so every computer names it the same. Different changes to one step are alternatives, shown under the step as "Two proposed changes", each decided on its own. A change to a step that changed between versions (another `base`) is a separate group. Describe and screenshot corrections are each their own group.
- **Decisions.** Anyone decides: Mark as applied (Applied to draft), Decline (a reason is required: "Why not? The runs will show this."), Reopen, and Withdraw (only whoever suggested every correction in the group). Each decision is a new file written once, `corrections/<process>/<group>.<window>.<rev>.json` (`repo.decideCorrection` refuses if that name exists): `{kind: "correction-decision", group, members, status, reason, by, at, rev, seen, act}`. Ordering is causal, never by clocks: `rev` is one more than the decision the decider saw, `seen` names its file; the highest `rev` counts. Two at the same `rev` were made at once: one is picked by file name the same way everywhere, and the group stays open, counted and listed under Open as **Needs review**, until someone decides again. A withdrawal by anyone but the author is ignored. A correction suggested again joins an applied group, and reopens a declined or withdrawn one ("Suggested again after it was declined: …").
- **No version-number stamp.** The old rule that marked an accepted suggestion "Fixed in vN" when any newer version was published is gone; applied reads "Applied to draft" until a version both lists it and makes it ("Published in vN", slice 3, below).
- **Legacy.** Suggested fixes (`kind: "fix"`) and checklist-change notes (`kind: "map"`) load as Describe corrections (their kind as a lead-in, their text as the problem). Their decisions in `suggestions/` are still read: accepted reads **Applied (legacy)** ("Applied before 1.16. Flightdeck can't confirm which version has it.") with **It's in vN** only; declined and reopened carry over. Nothing writes `suggestions/` any more.
- **The run's record.** The selected step lists its Corrections · N (badge on the row: "Correction proposed" or "N corrections"); the finish page and the receipt list **Corrections · N** for the whole run in checklist order: the step, Checklist said, Suggested (a redline for wording), Why or Problem, What happened, who and when, files, and a status pill (Open, Applied to draft, Declined with its reason, Withdrawn, Needs review, Applied (legacy), or One-off for a step done differently just this run). The plain-text receipt has matching lines. Corrections can be added after a run ends; they never change its outcome. A correction alone adds no mark, so it doesn't make a run unclean for readiness; a step done differently does, as before.
- **The process page.** "Corrections · N open", Open/All, grouped by step in checklist order (steps no longer in the checklist last), each group with its op, status, Checklist said, Suggested, every member's Why and What happened, files, Suggested in N runs, and its decision with who, when and why. Copy correction brief gives an AI assistant the open groups with the step as the draft has it now, people's words quoted as data, and attached file paths. Steps with open corrections are marked in the draft editor's preview.
- **Assistants** read `corrections/` and `suggestions/` and never write them, nor correction notes (`example-folder/AGENTS.md`, `/flightdeck-learn-from-runs`).
- **Applying to the draft (slice 2, 1.16).** An open group has **Review and apply** (**Review** for one Flightdeck can't make). It opens a dialog with a three-way comparison, side by side and stacked on a phone: **From the run's vN** (what the step said, and what was suggested), **Draft now**, and **Proposed result** (a redline against the draft for wording; who does it, or where the step is, when that's what changes). The draft compared is the draft editor's starting point when the editor is open in this window, else the draft in the folder, else the latest version, which applying makes the draft. `PF.corrections.review(group, text, edited)` says where it stands:
  - **clean:** **Apply to draft**. When the step has other open proposals (alternatives), it reads **Use this proposal**, and for wording alternatives **Combine into a new proposal** (a person's own wording; applying marks every combined group applied).
  - **already** (the draft says it already, apart from spacing; a missing step only at the place asked for, right after its step or last in its group; a removal whose step is gone): "This is already in the draft." with **Link this correction** (a decision only).
  - **changed** (the step, or the step a new one goes after, changed since the run's version): **Edit proposed result** (a box for wording or a new step's text; for other changes, a confirmation of what applies to the step as it is now) and **Already addressed**.
  - **gone** (the step, or what it moves after, isn't in the draft): **Already addressed** and **Decline** (with a reason).
  - **manual** (a screenshot, a described problem, a suggested fix from before 1.13, a change the builder's safety net refuses, "anyone" for a step whose lane has a role, a step whose ID two steps in the draft share): **Open in the editor** (the step selected in the builder, or its line selected in the Markdown) and **Mark as applied**.
- **How it applies.** `PF.corrections.toOps` turns a group into the builder's own operations (`PF.outline`: edit the text, add after the step or at the end of its group, move after a step or to the start or end of a phase, turn roles on and off, delete), each checked by the builder's safety net, so it changes only that step's lines and keeps every ID. The change is one named entry on the draft editor's Undo timeline ("Applied correction to "Post the release note""), saved at once through `repo.applyCorrection`, which works the result out again and saves it with `saveChecked` only over the exact draft compared (a draft that changed since is a conflict, shown in the editor like any other; no draft yet is created from the latest version, never over a file that appeared meanwhile). Applying is refused while this window has unsaved edits to that draft, an unapplied builder box, a conflict, a save in flight or an unreadable draft; the dialog says which. Undo of an applied correction is an unsaved change in the editor, which opens; saving it is a draft save like any other.
- **The decision follows the draft.** Only once the draft is saved is the decision written (`applied`, with `result`: `{step, sig}`, a fingerprint of the step as applied from `PF.corrections.outcome`; for a moved step its place counts too, and a new step is followed by its ID). If writing it fails, the draft keeps the change and the message says so; this window keeps what it applied (`state.corrApplied`, its outcome), so the next look finds it "already" in the draft even in the person's own words, and Link records it. If the draft itself can't be saved, the editor opens with the change as unsaved. Older copies ignore `result`.
- **Changed since applied** is worked out, never stored: an applied group whose decision recorded a result that the draft no longer matches shows "Changed since applied". Decisions without a result (Mark as applied before 1.16, a described problem) are never flagged.
- **Markers.** The builder's step rows and phase headings say "N open corrections"; the Markdown view lists **Open corrections · N** above the text with **Go to line N** for each step still in the draft; the preview keeps its badges.
- **Publishing lists what it includes (slice 3, 1.16).** At publish, `PF.corrections.forPublish(text, groups)` picks the applied groups not yet published whose change the exact text being published makes (a content check of what the change means, always: the step gone, the new step at the place asked for, the step's place, its roles, the wording. Applied ones whose step no longer matches what was applied are left out and named. The publish panel says "Included in this version: N corrections" and names those left out. Older copies ignore the field: `verify` and `unrunnable` read only what they check (unchanged since 1.11.1), runs don't copy publication fields, and `check_folder.py` ignores unknown keys (`test/checker.test.js`).
- **Published in vN (slice 3).** A group counts as in version N only when (a) vN's `publication.json` lists its ID, or a person's **It's in vN** decision names vN's folder, AND (b) vN's checklist makes the change (as at publish; a screenshot or a described problem can't be checked and relies on (a)). The stamp is the lowest N above the correction's own version (the lowest of its members') that passes; clashing versions never count. It's worked out from the folder each time (`PF.corrections.landing`, via `forProcess`) and never written into runs. The pill reads "Published in v5" everywhere a correction's status shows (process page, the run's record, the receipt). A later version with other edits never earns it by its number, and a listing whose step doesn't say it doesn't count.
- **Without proof.** An applied group Flightdeck can't place says so: "Applied before 1.16. Flightdeck can't confirm which version has it." (accepted before 1.13, or marked applied before 1.16: a decision without `result` or `dv: 2`, for a change Flightdeck can't check), or "A published version has this change but doesn't list it." (published by an older copy). It offers **It's in vN** for the non-clashing versions above its own (newest four), which writes a decision `{status: "included", version, folder}` (`dv: 2`, a new `rev` as usual, and the applied decision's `result` carried forward so a person's own wording is still recognized); (b) still applies.
- **Addressed differently.** **Already addressed** in the apply dialog (the step changed since the run, or is gone) writes `applied` with `addressed: true` and no `result`: the draft handles it some other way, so the correction reads "Addressed differently", is never listed when publishing nor named as left out, and gets a Published stamp only through It's in vN and the content check. **Mark as applied** for a change made by hand records no `result` either. Older copies ignore an `included` decision, so the decision before it stands there. Decisions written from 1.16 carry `dv: 2`.
- **Changed in vN on the next run (slice 3).** On runs of exactly the version that first has a group, its step (the new step for a missing one; none for a removal) shows a "Changed in v5" chip on its row, and the selected step shows it with a `<details>` **Why is this here?**: before and after (a redline for wording), the reason, "Suggested in N runs" with links to them, and who applied it. Runs of later versions don't show it.
- **Home acknowledgments (slice 3).** **Your corrections** on Home, apart from Needs you and never counted in it: one quiet item per process and version where the person's corrections were published ("Your correction to "Post the release note" is published in v5."), and one per correction of theirs someone else declined ("Casey declined your correction: <reason>."), each with **View change** (the process's corrections, All) and **Dismiss**. ## 23. Insights: how runs go (1.17)

Before 1.17, How runs go merged phases by title across versions, counted every answer rather than runs, gave no denominators, and lost a block once its answer was archived out of `run.json`. It also counted runs that couldn't be read and runs from a newer copy without saying so. Insights replaces it. The rules are in `core/insights.js` (`PF.insights`), which is pure and takes an explicit `now`; `views/insights.js` draws them.

**Inputs.** `PF.insights.forProcess(input, process, { now, folder, includeRunning })`, where `input` is what the app has accepted: `runs`, `runStatus` (`unread` or `missing` per run key, from the read results in section 25), `failedParts`, `decisionsUnread` (`corrections`, `followups`), `loading` (`{ done, total }` while a progressive load is under way), `corrections` (`PF.corrections.forProcess`) and `followUps` (`PF.followups.list`). `now` and `folder` are required.

**Groups.** Runs are grouped by their exact publication folder (`v5-k3m9p2q8`), never by version number, so two clashing v5 folders never merge; each is labeled Clash in the version picker. Versions are never pooled: Compare versions puts folders side by side, each with its own number of runs. Pooling would need a signature for when two versions' steps mean the same thing (frozen types, gate context, screenshots, order), which doesn't exist yet.

**What isn't counted, always listed.** A run whose file couldn't be read (its last copy is kept on screen), whose file is gone, or that a newer Flightdeck wrote (`_unrunnable`) is left out of every number, and the page says so with the runs behind it ("1 run couldn't be read; its last copy isn't counted."). While runs are still being read, every number says "Still reading runs (640 of 2,000). These numbers aren't final." A runs folder that couldn't be read says the numbers come from the last read. Decisions that couldn't be read flag only the follow-up or correction numbers. Bad times (one that can't be read, an end before its start, a gate before its phase began) leave the run out of that time only; it counts everywhere else. A run that didn't keep marks from its start (`marksFrom` isn't `"start"`) and shows nothing for a step is **history incomplete** for the "ever" numbers: counted apart, never as clean. Runs still going are listed under Runs and left out of the step and phase numbers, unless asked for (the flight plan asks, since it shows a version being flown). Durations over 30 days are shown; the follow-up age buckets are a policy, not a check.

**Definitions.** Each number has its own denominator. "Ever" numbers are a union of the run's durable `marks` for the step and every kind in its current and retained answers, so a block archived out of `run.json` still counts. Any off-script counts a run once however many kinds it had, so it is never more than the sum of its parts and never less than any one of them; the bars are separate, never stacked. Phase time starts at the previous gate's settle time (`created` for the first phase) and ends at this gate's (`passed` or `waived`, its `at`); a gate that isn't settled, was reopened (`was` present, state `review`, or back in review by the rules), or has a time that can't be used leaves out that phase and every later one, with the reason. Times leave out paused time (`R.activeMs`). A median shows from 1 run; the middle half (quartiles) from 5.

## 25. Large folders (1.17)

Planned in four slices; **slices 1a and 1b are built** (1.17.0). 1a: the measuring tools, explicit read results, safe parsing, paging, lazy thumbnails, one pool per folder, `go()` and the refresh-time check. 1b: freshness on an elapsed-time schedule, stamps that come with reads, and progressive loading. Section 23 is insights; sections 22 and 24 are reserved for search and evidence export.

**Measuring.** `tools/big-folder.js` makes a synthetic folder from a seed, byte for byte the same every time (even IDs the rules make up come from the seed): 200 processes, 600 versions (1 to 6 each, two clashing pairs), checklists of 20 to 120 steps (median 40, about 11 KB of `map.md`), 40% of versions with 2 to 6 screenshots; 2,000 runs (50 running, 100 ended in the last week) played through the real rules; 1 to 3 notes files per run and 10,000 notes; 2,000 attachments, recorded by size only; 300 decisions in `corrections/`, 1,500 in `followups/` and 40 legacy ones in `suggestions/`; and oddities (3% of runs with an orphan save receipt, 5 OneDrive copies, 3 unreadable `run.json`, 2 runs from a newer copy, runs without `marksFrom`). **Read results.** Loading returns one result per run key in `reads`, never a bare object: `fresh` (read now: `{run, build}`), `cached` (an ended run unchanged since it was read: `{fileHash, sig, build}`), `unreadable` (`{why}`), and, worked out by the app, `missing` (not in a **complete** listing of `runs/`, `runsComplete`) and `pending` (not read yet; never means missing). The app applies them in `applyRunRead`: only a fresh read clears "couldn't be read" or "gone"; a cached result never changes a run's status, keeps what's shown when its signature (`repo.runSig`: file, notes, copies, read-only reason) matches, and otherwise builds a new object. Runs whose last check failed are always read fresh. Read order (`applied`, `seq`), `canReplace`, pending-save guards, candidate grace times and `keepUnread` are unchanged. `loadAll(...).runs` still lists every run, built on first use.

**Cache entries can't be changed.** The ended-run cache keeps a frozen entry: `run.json`'s text, each notes file's text, the copies found, the read-only reason and when to look again. Every object is built new from it (`R.sanitize(JSON.parse(text))`, as a fresh read does), so an edit on screen can never leak into what the folder said. Discard goes back to a version built new from what was read or saved (`baselines[id].make()`), never to an object anyone can change. Runs of one version share one `snapshot` string and one `types` object, but only when they're equal. Since 1b the cache keeps running runs too (`cache.runs`, the plan's `cache.live`), through the same frozen entries, and every write this window makes into a run folder (a save, a conflict copy, a note, keeping or removing a copy) drops that run's entry, so the next refresh reads it even if the save left the same size and time. If a cached result is ever older than the run shown (a lower `rev`), the app ignores it and reads that run fresh next time.

**Sizes come with reads.** `FolderFS.read` returns `{text, mtime, size}` from one `getFile()` (a file that changes while it's read fails to read), and so does the examples folder (UTF-8 bytes). A notes file read with its size is remembered under that size and time, without a second `stat`. Since 1b, reading a run records each file's stamp (size and time) from the very read that returned its text (`entry.stamps`); only files not read (copies, save receipts, history) are stat'ed, and the run folder is listed once more after reading. The run is cached only if it still holds the same files, under the stamps of the texts read, so anything that changed after its read shows up as a different stamp at the next check. A folder whose reads don't give their size (`cache.sized` false) keeps the old way: fingerprint before and after reading, cached only if they match. A first open costs about 4.5 calls per run instead of about 11.

**Freshness by elapsed time (1b).** Size and time are only a shortcut: they can't prove a file is unchanged (a sync tool or editor can keep both), so every cached run also has a maximum content age, after which it's read in full, bypassing the run and notes caches. Ages are elapsed time, never a count of refreshes. Two clocks feed it: the monotonic one (`loadAll(fs, {clock})`, `performance.now()` by default), which some systems pause while the computer sleeps, and the wall clock (`{now}`, `Date.now()` by default), which a person can change. The time since the last refresh is the larger of the two, counted once and never added, and kept as the folder's own running total (`cache.clk`); the monotonic clock going backward, or the wall clock going back by more than 2 minutes (`BACK_MS`), makes everything due; a smaller step back while the monotonic clock moves on (time sync) counts as no wall time. So setting the clock back never delays a reread, and 8 hours asleep count as 8 hours. Each run's entry keeps `metaAt` (its last size-and-time check) and `contentAt` (its last full read). On each refresh (`planRuns`):

- a run not known yet, one asked for fresh (its last check failed, or its cached copy was older than the one shown), one past a save receipt's grace time, and every run on Refresh (deep) is read;
- one past its maximum content age is read in full: `config.endedMs` (60 minutes) for a finished run, `config.liveMs` (5 minutes) for a running run that isn't open;
- a running run, or one that ended in the last week (`config.recentMs`, by its own end time against the wall clock: a clock set back only makes more runs recent), gets its sizes and times checked (one list, a stat per file) on every refresh, and is read when they differ;
- an older finished run gets that check within `config.metaMs` (10 minutes);
- the rest cost nothing.

Each kind takes its share of the time since the last refresh (keys × elapsed ÷ maximum age, carried over between refreshes), oldest first, plus anything already overdue, so the work is spread evenly instead of arriving all at once at the 10- or 60-minute mark. A full read's age outlives the cache entry (`cache.contentAt`): this window's own writes drop the entry, but the next read, which may take unchanged notes from memory, keeps the age of the last full read, so saving often never postpones another computer's same-size edit past the maximum age. Every read checks that age (`overdue`), whatever started it (no cache entry since this window wrote, or sizes and times that changed), and reads in full when it's past; so does the open run's 5-second reread (`loadRun`, against the folder's elapsed time between refreshes, `peekNow`), which otherwise takes unchanged notes from memory. Reads go first (overdue runs after a hidden tab or a pause), then checks. A hidden or busy tab reads nothing, as before. The app's refresh timer uses the same two clocks, and when the tab is shown again, the page restored or the network back after more than a minute on the wall clock without a beat (the computer slept), it refreshes at once; a plain window focus rereads only the open run when one is open. The open run keeps its own reread every 5 seconds (run.json in full, notes by size and time, all of them past the 5-minute age). Decision files in `corrections/`, `suggestions/` and `followups/` are listed on every refresh; a file is read when it's new, when it couldn't be read or understood last time (that's never kept, so it's tried every time), on Refresh, or past the hour, a share each refresh. Otherwise the text from its last read is used (`cache.dec`), and a file gone from the listing is forgotten. So a late note on a month-old run arrives within 10 minutes, or within the hour if its file kept its size and time, and Refresh reads it now.

**Progressive loading (1b).** `loadAll(fs, {onBatch, priority, batch})` hands over fresh and unreadable results as they arrive, `config.batch` (100) at a time, with `done`, `total` and the keys still `pending`. A batch never contains `missing`: only the final, complete result can mark a run gone, through `applyRunsRead`. The app applies each batch through `applyRunRead` with the load's own start (`seq` and revisions), so an edit, a save, a restore or a newer read of the run since the load began wins, exactly as for the final result, and a batch from a folder switched away from is dropped (`gen`). Order comes from the last accepted state (`readPriority`): runs known to be running first, then runs that ended in the last week, then keys this window doesn't know yet (new folders are likely new runs), then the rest. On the first open of a folder there's no prior state, so until the first complete read Home says "Still reading runs (640 of 2,000). Runs you're recording may not be listed yet." and Runs says "Still reading runs (640 of 2,000). Runs not read yet aren't listed." (`state.reading`); neither says there's nothing. Insights labels its numbers not final while that shows (section 23); search will too.

**One parse per checklist.** `R.mapOf` keeps one parsed map per `folder|mapHash`, used only when the run's `snapshot` is exactly the stored text. The app keeps entries the loaded runs use (`R.mapMemo.keep` after each accepted load) and clears them when the folder changes, so there's one parse per distinct checklist per folder generation and no fixed size for many interleaved versions to thrash. The map is shared: nothing may change it. Tests deep-freeze it (`R.mapMemo.freeze`), along with the shared step types.

**Paging.** Runs › Running and Runs › Finished show 50 at a time (`PF.vk.paged`): "Showing 50 of 1,950" and **Show 50 more**, which moves focus to the first run it added. The first view draws at most 100 cards; paging (not scroll virtualization) keeps Ctrl+F, screen readers and patching working. 500 cards render in under 250 ms in the views test.

**One pool per folder.** `repo.poolOf(fs)` is one pool of 8 calls per folder, shared by loading, the open run's reread and thumbnails (export will join it). Waiting calls start in lane order: the open run, then loading, then thumbnails (at most 4), then export (at most 2). Folder health's scan keeps its own 8.

**Lazy thumbnails.** A thumbnail is a placeholder until one shared `IntersectionObserver` sees it; then it's read and shrunk as one job in the pool's thumbnail lane. A job is bound to the folder and generation it was queued in and stops before reading if either changed. Placeholders a redraw removes stop being watched. Which placeholders are watched is what the observer tracks right now, never a mark on the page: after every redraw, each placeholder with no picture and no job running is watched again, so a placeholder a redraw kept (moving to another run of the same publication at the same step) loads even when its earlier job's result was thrown away. Switching folders cancels what's waiting. Browsers without `IntersectionObserver` load thumbnails at once, as before.

**`go(target)`.** One way to jump to `{view, process, ptab, mapVer, run, step, note, filter}` (action `go`). It goes through `setView`, so typed evidence, an open Fill in and an unsent note are kept as drafts and come back; it unfolds the phase, selects the step, moves focus to its row and flashes it (or the note). Input held in app state belongs to the context it was typed in and is never thrown away by leaving it: `leaveContext()` runs first in every change of context (`setView`, `selectStep`, opening a correction), before any state key is reassigned, and keeps the departing context's typed boxes (its step's draft), open Fill in and correction being written (including Move it to and Who should do it; `corrDrafts`, keyed by folder, run, step and mode). `enterContext()` brings back only the destination's own. A composer on screen is always kept before another opens, never written over; opening another small form on a step (Blocked, a deadline) keeps its open Fill in the same way, and Fill in draws its action and the fields for that action from one draft (the step's draft over its latest choices), so they always agree. Every folder change (opening a folder, Reconnect, the examples) first keeps typing as drafts of the folder it was typed in (every draft key carries the folder), then closes what's open, so nothing typed in one folder shows or is saved in another; files picked but not attached stay in `pendingFiles`, keyed by run and step; a submitted, refused New process form stays in `newProc`, and each form carries a token that changes when it's opened, submitted or typed in, so a creation that finishes late clears and leaves only a form unchanged since that submit; otherwise it keeps the form and says where the draft is. Each comes back on return and is cleared only by Cancel, a successful save, or switching folders. A dialog holding choices (Review and apply: an edited result, alternatives being combined, a decline started) says so with `held()` and isn't closed. For typing that isn't in state yet, it refuses rather than lose input, and it asks the page, not a list: the first control on the page or in an open dialog whose value isn't what the page drew (value against `defaultValue`, checked against `defaultChecked`, the chosen option against the one drawn as chosen) holds unsaved typing, so a new form is covered without being registered. Skipped: what's kept as a draft (`data-draft-kept`: the note, evidence, Fill in, the draft editor and the step-type form), search boxes and anything marked `data-nav-safe`. Typing in a builder box says "Apply or clear what you typed in the box first…"; anything else says "Finish or cancel this first.", and focus goes to it. A dialog with nothing typed in it is closed first; one with typing is never replaced. A phone's step sheet is closed first, and the target row is scrolled into view (`scrollIntoView`, nearest), in the run already open too. Keys are ignored while an input method is composing.

**Folder health.** The run thresholds stay at 500 (warn) and 2,000 (stop) until 6,000-run and real-browser measurements support a change. The one addition is measured, not counted: the refresh-time check in section 21.
