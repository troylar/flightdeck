# Two-computer rehearsal waived (not rehearsed): Flightdeck 4.0.0

- Version: 4.0.0
- Date: 2026-11-15
- Decision: the project owner waived the two-computer rehearsal (docs/rehearsals/README.md, *The release gate*) for this release, under the owner's standing rule that a waiver is recorded, not asked for. No rehearsal is planned.

## Why it was required

4.0.0 is a major release. It adds living runs: to-dos a run takes on while it runs, kept as to-do records in `proposals/` (`flightdeck-plan/4`, `flightdeck-plan-status/4`) and landed by the recorder's window into `run.json` (`preflight-run/3` naming `living-runs`), with spreads, facts, keeps, checklist-linked to-dos, plan versus now and the receipt a living run ends with. Several windows on several computers write those records at once, and the recorder's window lands them through the checked save chain. A run without to-dos reads and saves as in 3.0.

`src/storage/repo.js` also changes how every write reaches the folder. A run save, a conflict copy, a scope or to-do record and a receipt each read what they depend on again right before each write (`opts.fresh`, then `opts.recheck`, then `opts.still`). The app installs a write gate (`repo.gateWrites`): a run file or a scope or to-do record is written only with a token minted for exactly that write, and the plain writers refuse them. In `src/ui/app.js`, `mutateRun`, `recover` and the save queue carry those guards, and a change a guard refuses is put back on the run it changed, never kept for Try again.

## What the rehearsal would have covered

On a test folder, with two computers on 4.0.0 and a third on 3.0.1:

- To-dos asked, decided and delegated on one computer while the recorder's window on the other lands them.
- A delegation revoked, a blocker fact filed or people.json changed on one computer while the other is part way through a landing: nothing more is written, and the landing is put back.
- A spread added and synced to a loop's stories, and a loop's approval given while a story's run changes on the other computer.
- Facts filed by a tool, and a to-do checked off on a story's evidence.
- A keep made from a correction, and its review by the checklist's owner.
- A living run ended with its receipt while a request arrives on the other computer.
- An evidence pack made of that run.
- The 3.0.1 computer opening the same folder: it shows the new records by name and writes nothing to them.

## What covers it instead

Automated tests in `./test/run.sh`, all passing on the release commit:

- The to-do, spread, fact, keep, checklist-linked and receipt rules (`test/todos*.test.js`, `test/spreads*.test.js`, `test/facts.test.js`, `test/learn.test.js`, `test/detours.test.js`, `test/receipts.test.js`, `test/loops.test.js`).
- The write gate and its guards (`test/guards.test.js`): every plain writer refuses a run file or a scope or to-do record, a token is good only for the write and folder it was minted for, and the source writes through the gated writer only.
- The app suites (`test/app-todos*.test.js`, `test/app-spreads.test.js`, `test/app-spread-deps.test.js`, `test/app-facts.test.js`, `test/app-learn.test.js`, `test/app-detours.test.js`, `test/app-receipts.test.js`): interrupted writes, a person switched mid-write, a blocker or a revoke at each write of a landing, a request landing between the receipt and the run's save.
- The command and checker parity rules (`test/checker-todos.test.js`, `test/*-cli.test.js`).
- The evidence rules (`test/evidence-living.test.js`, with Python's independent replay of the chain).
- The cross-version tests against the exact shipped 3.0.1 (`test/compat-todos.test.js`, `test/compat-receipts.test.js`).

## What remains unproven on real OneDrive

- How to-do records, applications and receipts written on one computer arrive on another while OneDrive is still syncing (late, out of order, or as conflict copies).
- How the recorder's window behaves on a folder that is a minute behind, when the read right before a write sees an older file than the other computer wrote.
- A mixed team (3.0.1 and 4.0.0) sharing a folder with living runs over real sync delays.

The tests stand in for OneDrive with in-memory and on-disk folders. Real-OneDrive behavior is unproven, and every step above still needs a manual rehearsal.
