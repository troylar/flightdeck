# Two-computer rehearsal waived (not rehearsed): Flightdeck 2.8.0

- Version: 2.8.0
- Date: 2026-10-27
- Decision: the project owner waived the two-computer rehearsal (docs/rehearsals/README.md, *The release gate*) for this release.

## Why it was required

2.8.0 adds a new required feature to existing formats: `passed-details` on a version (preflight-publication/2) and on its runs (preflight-run/3), from a `pass:` line on a Run another process step. It also changes `src/storage/` (publishing and staging read every linked child from the folder at that moment, not only pinned ones) and the saving code in `src/ui/app.js` (starting a child checks again, just before the write, that nothing it passes changed). By the rule in docs/rehearsals/README.md, it needs the rehearsal.

## What the rehearsal would have covered

The script's steps 0 to 25 and the accounting tally, run once with both computers on 2.8.0 and once with one computer on 2.7.0 and one on 2.8.0, on a test folder holding:

- a checklist whose linked step uses only `carry:` (it must publish exactly as on 2.7, and both computers record on it as before);
- a checklist with a `pass:` line (2.7.0 names it "needs Flightdeck 2.8" and starts nothing);
- a child started from computer A while computer B has the parent run open, and the parent's passed detail changed on B while A's start form is open (nothing starts on A, and it says why);
- a child republished on one computer without a detail a step passes, while the other publishes the parent.

## What covers it instead

Automated tests in `./test/run.sh`, all green on the release commit:

- **Older copies, from their own shipped code** (`test/compat-harness.js`, every tag recorded from 1.10.0 to 2.7.0, with the floor at 1.11.1): `test/compat-pass.test.js` (a version with `pass:` and its run/3 refused by name by every older copy, nothing started or written; a checklist without `pass:` stays readable and recordable), plus `test/compat.test.js`, `test/compat-formats.test.js` and `test/old-bundles.test.js`.
- **File formats**: `test/envelope.test.js` (the lowest sufficient format, frozen samples byte for byte).
- **What a step passes**: `test/links.test.js` and `test/refs.test.js` (reading and writing `pass:`, the publish checks against the child as it is now, rename keeping each child detail's value).
- **Starting a child**: `test/app.test.js` (the start form filled in, asked values kept across a refresh, a bad value, a failed save, and search or Back; nothing starts when a passed detail changed meanwhile).
- **Reading children from the folder**: `test/cli.test.js` (`draft read` is partial when a child can't be read or a newer child version is damaged).
- **Two computers, simulated**: `test/sync.test.js` and `test/app.test.js` (the built app with races paused at exact points).

## What isn't proven on real OneDrive

- A child started on one computer while the other changes a passed detail, over real sync delays: the write-time check sees only what has arrived.
- A child republished on one computer while the other publishes the parent: the parent's publish checks the child as its own copy of the folder has it.
- A mixed team (2.7.0 and 2.8.0) over real sync delays.

## What still runs by hand

The one-computer browser check in Edge and Chrome from a real `file://` path: link a step to another checklist, set where each detail comes from, publish, start a run, start the child from the step and fill in what it asks.
