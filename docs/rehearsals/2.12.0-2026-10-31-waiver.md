# Two-computer rehearsal waived (not rehearsed): Flightdeck 2.12.0

- Version: 2.12.0
- Date: 2026-10-31
- Decision: the project owner waived the two-computer rehearsal (docs/rehearsals/README.md, *The release gate*) for this release.

## Why it was required

2.12.0 adds AI assistant files to Settings, which changes `src/storage/`:

- `src/storage/fs.js`: `mkdirExclusive` is new, on both file systems.
- `src/storage/repo.js`: `contractWrite`, `archiveDir`, `archiveCopy`, `archiveStaged` and `stagedOf` are new, and `repo.scan` also reads the copies waiting in `.flightdeck/updates/<version>/` and keeps the record's text.
- `src/core/health.js` (the gate names it for the connection check): Folder health's `contract` check now decides through `PF.contract.classify`. The connection check isn't touched.

`mutateRun`, `canReplace`, `recover`, `applyRunRead`, `useFs`, `acceptProposal` and `queued` are byte for byte as in 2.11.1, and `saveChecked` is used as it is. The run and notes formats aren't touched. `AGENTS.md`, the skills, `.flightdeck/installed.json` and `.flightdeck/updates/` now have a second writer, the app, alongside `flightdeck install`, with the same rules and the same record format.

## What the rehearsal would have covered

On a test folder, with one computer holding the folder open while the other acts:

- Update on one computer, then the other computer seeing the new files, the record and Folder health's result.
- Update on both computers at about the same time.
- Update while OneDrive is still bringing down a newer `AGENTS.md`.
- I merged it on one computer while the other has the screen open.
- Update on 2.12.0, then `flightdeck install --check` from an older package on the second computer.

## What covers it instead

Automated tests in `./test/run.sh`:

- **The same rules as the command**: `test/assistant-files.test.js` compares the core's `readRecord`, `classify`, `nextRecord` and `mergeReadme` with `bin/flightdeck.js` case by case, and compares the contract part of a folder after the app's Update with the same folder after `flightdeck install`, across folder states. Folder health, Settings and `install --check` are compared on each state.
- **A file changing during an update**: a write between the app's read and its write is skipped, named and keeps its old record entry.
- **Copies**: a copy that doesn't read back stops the replacement. I merged it removes a waiting copy only after the copy reads back and the source is unchanged.
- **Switching folders**: a running update stops before its next write, and writes nothing to the new folder.
- **The record**: `installed.json` written by the app is read as valid by `flightdeck install`. Older copies' reading of `by: "app"` is the command's existing check; an older package wasn't run against it in the new test.
- **Everything else on saving and reads**: `test/sync.test.js`, `test/folder.test.js`, `test/app.test.js`, and the compat tests from older releases' shipped code.

Full suite: 125 jobs, 0 failed.

No browser run. The app harness has no layout, and its folder handle is a stand-in for the real File System Access API.

## What isn't proven on real OneDrive

- A skill file or `AGENTS.md` replaced by the app arriving on a second computer, and what OneDrive does if that computer changed it at the same moment. The app's exact-text check only sees what this computer has received.
- Two computers pressing Update at about the same time. Each checks before it writes, but a folder can't check and write in one step, so OneDrive may keep both copies of a file. Folder health's existing conflict-copy check is what would show that.
- `mkdirExclusive` and `fs.remove` on OneDrive's placeholders and online-only files.
- A copy read back from a real OneDrive folder right after writing it, which the tests only prove on a stand-in.
- The real browser's permission prompts: a remembered skills folder asking again, permission withdrawn while the screen is open, and the picker refusing a folder.
- Folder health's scan reading waiting copies on a slow real sync.
