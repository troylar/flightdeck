# Two-computer rehearsal waived (not rehearsed): Flightdeck 3.0.0

- Version: 3.0.0
- Date: 2026-11-08
- Decision: the project owner waived the two-computer rehearsal (docs/rehearsals/README.md, *The release gate*) for this release, under the owner's standing rule that a waiver is recorded, not asked for.

## Why it was required

3.0.0 is a major release with two must-understand format changes. Module results (feature `module-results`) add `result:`, `sets: <detail>=decision|result` and `accepts:` to checklists, and a run/3 that uses them records which answer a linked step counted. Loops (feature `loops`) add the `{for.each}` step, run/3 children that name the item they were started for, and scope records in `proposals/` (`flightdeck-plan/3` requests and `flightdeck-plan-status/3` decisions), each written once and never replaced. Copies before 3.0 refuse both features by name and write nothing.

`src/storage/repo.js` reads scope records in `proposals/` with their own reader before the plan reader, gains `saveScope` (an exclusive write of a new file), and lets a run save carry a guard that is asked again right before each write, so a folder switch or a changed run writes nothing more and leaves a written candidate where recovery finds it. In `src/ui/app.js`, every write of a loop's parent or child goes through one guard builder and the save funnel, and a dropped change is put back only on the run object it changed, in its own folder generation. The gated functions (`queued`, `canReplace`, `applyRunRead`, `useFs`, `acceptProposal`, `mutateRun`, `recover`) are byte for byte as in 2.16.2.

The release also carries the library view (`flightdeck library inspect`, Used by and similar, design tips) and `check_folder.py --draft`, which only read.

## What the rehearsal would have covered

On a test folder with a checklist that returns a result and a `{for.each}` loop over it, both computers on 3.0.0:

- A linked run's decision recorded on one computer while the other has the parent open: the step settles once, in the recorder's window, and a passed gate goes to review.
- The linked run reopened or corrected on one computer after the parent counted it: the parent's step settles again.
- Two computers changing the same loop item at once (an exception given on one, the item removed on the other): both records arrive, the item is held for review, and the approval stays held until a person settles it.
- A scope request filed from the command line on one computer and carried out by the recorder's window on the other, with a retry of the same key after a lost receipt.
- Start all on one computer while the other switches folders or changes the run: the batch stops, says why, and starts nothing more.
- An approval given on one computer, then a change arriving from the other: the approval goes back to review with the change listed.

And with one computer on 2.16.2 and the other on 3.0.0:

- A checklist with a result and a loop published on 3.0.0: 2.16.2 lists them by name, can't run them and writes nothing to them or their runs.
- Scope records in `proposals/` arriving on 2.16.2: never offered as a plan, never written.

## What covers it instead

Automated tests in `./test/run.sh`, all passing on the release commit:

- `test/results.test.js`: the syntax and its blockers, settling a step by its run's answer, held steps, sticky review, ended parents and contract 2's new fields.
- `test/app-results.test.js`: the recorder's window settling again when a linked run's answer changes, Start a new run on a held step, escaped and read-only results, and the Publish panel's notice.
- `test/loops.test.js`: the scope ledger and its causal order (records ordered by what each saw, never by clock), every conflict holding approval, settling 50 records at a time, plan and run choices, feeds bound to one source, and every scope record checked as a reader will read it before it is filed.
- `test/app-loops.test.js`: the run screen's loop table, one guard on every loop write through the save funnel, recovery, its backup and restores, a dropped change put back only on its own run (tested with a copied folder holding the same run key), and Start all stopping with a reason.
- `test/loop-cli.test.js`: every `flightdeck loop` command, the same key as the same request, `--dry-run` previews, and paging words.
- `test/compat-results.test.js` and `test/compat-loops.test.js`: every recorded release refusing results and loops by name and writing nothing.
- `test/library.test.js` and `test/checker.test.js`: library inspect, design tips, and `check_folder.py` giving the same blockers word for word.
- `test/perf.test.js`: 50 and 60 decisions made at once and a 2,000-record history settle within their budgets.
- The compatibility, recovery and save round-trip suites (`compat-*.test.js`, `save.test.js`, `failed-reads.test.js`, `sync.test.js`) on the new formats, against every recorded release through 2.16.1 (2.16.2 changed only what screens show).

Also on the release commit: eleven rounds of code review on loops, each finding fixed with a test written to fail first.

## What remains unproven on real OneDrive

- Two loop records written at once on two computers, delivered by real sync in either order.
- A command-line request filed on one computer and carried out by the recorder's window on another, over real sync delays.
- A linked run's answer changing on one computer while the parent's recorder is on the other.
- A mixed team (2.16.2 and 3.0.0) sharing a folder with results and loops over real sync delays.
