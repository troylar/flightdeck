# Two-computer rehearsal waived (not rehearsed): Flightdeck 2.14.0

- Version: 2.14.0
- Date: 2026-11-03
- Decision: the project owner waived the two-computer rehearsal (docs/rehearsals/README.md, *The release gate*) for this release.

## Why it was asked for

2.14.0 is a minor release that adds a command which writes to the team folder: `flightdeck type save` writes `step-types/<id>.json` and one history line. Nothing changed in `src/storage/`: every file there is byte for byte as in 2.13.0, including the app's own step-type save, `safeWrite`, `writeNew`, the loaders, the run and notes formats, the connection check and `mutateRun`. The new write code is in `bin/flightdeck.js` (`type list`, `type read` and `type save`) and in `src/core/save.js`, which decides the outcome and its words; `src/core/types.js` gains the file text, the unused-key and in-use warnings, and `src/core/appjson.js` the `flightdeck-write/1` contract. `type list` and `type read` only read. The release ships a rewritten new-step-type skill, written by the existing writers, `flightdeck install` and Settings > AI assistant files, with the same rules and record as 2.13.0. `AGENTS.md` is unchanged.

## What the rehearsal would have covered

On a test folder, with one computer on 2.13.0 and the other on 2.14.0:

- Saving a step type with `flightdeck type save` on 2.14.0, and the other computer's Step types page and editor showing it, its history line and the checklists that use it.
- Editing the same type in the app on one computer while the command saves it on the other, and each side's stale-save check refusing the older text.
- Update on one computer, then the other computer seeing the new skill, the record and Folder health's result.

## What covers it instead

Automated tests in `./test/run.sh`:

- **The outcome rules:** `test/save.test.js` checks the order of refusals, every outcome's words and exit code, the copy rules and the history warnings, and refuses rows that can't happen.
- **The command on real folders:** `test/type-cli.test.js` runs `type list`, `type read` and `type save` on temporary folders, with hooks that change, replace, remove or link the file at each step of the save (before the compare, after the final listing, after the link and after the rename), and requires the outcome, the words, the exit code, what's on disk and the history line for each; links, symlinks and folders where a file should be are refused, and nothing is written outside the team folder.
- **Reads that fail:** `test/type-guards.test.js` breaks every input each command reads (`step-types/` and the type, `people.json`, the drafts and the type's history) every way a read can fail (a listing that fails, a file or folder that vanished after it was listed, access denied, a file too big, a link), and requires a problem named, `complete` false, never `missing` or rev `none`, a held save's next step that fits the failure, and a draft or history check it couldn't finish named in its warnings.
- **The same view as the app:** `test/cli-parity.test.js` requires `type list` and `type read` to agree with this build's Step types page on which files load, in which order, which are copies and past the 100-file limit, and what each loads as.
- **Older copies:** `test/compat-typesave.test.js` loads the command's file in every recorded release and requires the same normalized definition (1.10.0 refuses `group` and `tags`, as it always has), checks that 1.x copies refuse a /2 type by name, that the history line is read from 1.16.0 on, and how each release's editor treats a stale save over the command's bytes.
- **Storage unchanged:** the app, staging, pins and publish tests of 2.13.0 run unchanged; the roles comparison runs against 2.13.0's shipped page.
- **The text:** `test/docs.test.js` checks `docs/apps.md` names every command in the help; the skill and the help carry the same sentence about two saves at the same instant.
- **Upgrading:** the install, Settings and upgrade tests run against the new defaults, recorded in `src/baselines.json` for 2.14.0, and the cross-version tests run every recorded release, now with 2.13.0.

## What isn't proven on real OneDrive

- A step type saved by the command on 2.14.0 arriving on a computer on 2.13.0, and the new skill arriving while that computer has one open.
- How OneDrive's own copies (a file renamed with a computer's name, or with a number) appear when two computers save the same type within a minute.

## Limits that are known and kept

- **Two saves at the same instant:** like two Flightdeck windows in different browsers, two saves at the same instant can replace one another without either being told. The command reads back what it wrote and says `replaced`, `unverified` or `unsure` when it sees a sign of that.
- **A minute behind:** the command reads this computer's copy of the folder, which another computer may be ahead of.
- **The 100-file limit:** past it, `type save` warns and still saves; which files to remove is a person's call.
